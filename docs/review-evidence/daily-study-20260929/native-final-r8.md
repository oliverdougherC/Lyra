# Final-code isolated native diagnostic — September 29, 2026

## What ran

The tested frontend assets and frozen Python sidecar were built from #98 code
`7d9e447fdb49a58a1675e056d7980cd3365ed5b6`. The diagnostic copied the
production `dist/assets` bytes unchanged; its `index.html` adds only an
event-driven timing overlay and a separate minimal control page. The frozen
backend executable SHA-256 matched the production review staging copy.

The signed Tauri variant retained the established isolated restart setup:
compiled ID `com.lyra.pla570.restart`, a fixed separate persistent WebKit
data-store identifier, disposable `/private/tmp` backend profile, and null
Keyring. Bundle verification checked 77 arm64 objects. It used one synthetic
class, a 122-message transcript (60 added user/assistant pairs with math,
lists, and code), a 12-page synthetic PDF, and a deterministic loopback tutor
that streamed mixed Markdown. The normal installed app was neither launched
nor replaced. This setup tests actual native chat and page UI, while differing
from production in native identity, WebKit store, backend paths, Keyring, and
the timing overlay.

this session ran on AC power with macOS 27.0 (26A428), WebKit 22625, and
an Apple M4 Pro. The following intervals start and end in JavaScript. The
overlay runs `requestAnimationFrame` only for 500 ms after input, key, pointer,
or scroll activity and does no idle frame loop. Native accessibility automation,
the overlay, and process sampling add overhead.

A targeted 10-second `/usr/bin/sample` trace of the final-code WebContent
process during the mixed stream found most main-thread samples in the run-loop
wait (`5,876` of `7,102` samples), with timer dispatch and WebCore paint,
style, layer, and layout work in active samples. JavaScriptCore compilation
and allocation also appeared. The trace does not label React components or
presented frames, and accessibility queries affect the call tree. Raw traces
and process JSON remain private under `/private/tmp/lyra-r8-*`; this summary
contains no user documents, request content, or credentials.

## Conclusion and supported paths

The simple control repeated near 60 callbacks per second in the same WKWebView
that hosted Lyra, despite the 120 Hz display setting. The actual chat's
streaming tail is worse than the control, so app work and runtime pacing both
remain relevant. This is a reproducible **callback-path limitation on this
machine and OS build**, not proof of a universal WebKit limit or a presented
60 Hz ceiling. WebKit's [open request for a public WKWebView high-refresh
option](https://bugs.webkit.org/show_bug.cgi?id=294338) matches the missing
supported control; Apple's [WKWebView API](https://developer.apple.com/documentation/webkit/wkwebview/)
does not expose a frame-rate preference. Apple's
[display-link preference](https://developer.apple.com/documentation/quartzcore/cadisplaylink/preferredframeraterange)
applies to a native display link, whose callbacks are still subject to system
policy; it is not a switch for this WKWebView.

Supported next options are to remeasure when a public macOS/WebKit high-refresh
path appears, continue bounded profiling of the measured streaming paint/layout
tail, or isolate only an interaction that truly needs 120 Hz into a native view
using public Apple APIs after product review. No private WebKit API, forced idle
repaint, or framework rewrite is part of this candidate. Presented scrolling
frames, physical input-to-paint, production-default WebKit/Keychain behavior,
and a repeated hidden-idle distribution remain unverified; PLA-570 stays open.
